# gameWE collector - notes for Claude

Go daemon (`module gamewe-collector`, Go 1.27) that receives Source engine
log lines over UDP, parses them (`internal/logparse`), writes stats into the
HLstatsX/gameME schema on MariaDB/MySQL or PostgreSQL (`internal/stats`,
`internal/database`) and answers in-game commands over RCON
(`internal/rcon`, `internal/collector/reply.go`). Config: YAML
(`config.example.yaml`, installed as `/etc/gamewe/collector/config.yaml`),
game servers and their `rcon_password` live in `hlstats_Servers`.

Build and test: `make` (vet + test + build), `go test ./...`, integration
tests need a database (`-tags integration`, see `.github/workflows/build.yml`).

Releases: Conventional Commits + semantic-release (`.releaserc.json`). Every
push to `main` is built and tested and the image is published as
`ghcr.io/dennispohlmann/gamewe-collector:edge`; `feat`/`fix`/breaking
commits make semantic-release bump the version files, write `CHANGELOG.md`,
commit `chore(release): vX.Y.Z [skip ci]`, tag `vX.Y.Z` and publish the
GitHub release with the archive (+ sha256) and the image tags `<version>`,
`<major>.<minor>`, `latest`. There is no tag-triggered workflow.

## Documentation layout (the same in all gameWE repos)

- Root: `README.md` (overview, requirements, quick start, documentation
  table, components, building, license), `CHANGELOG.md` (generated),
  `LICENSE`, `THIRD-PARTY-LICENSES.md`, `CLAUDE.md`.
- `docs/`: `INSTALLATION.md` (install, update, uninstall, troubleshooting),
  `CONFIG.md` (all settings), `USAGE.md` (commands, pages, operation),
  `INTERFACE.md` (log lines, RCON commands, APIs between the components),
  `DEVELOPMENT.md` (build, tests, CI, releases); repo-specific extras:
  `DATABASE.md`, `DB-SEMANTICS.md`, `GAMES.md`, `MIGRATION-HLSTATSX.md`,
  `MIGRATION-GAMEME.md`, `migration/` (SQL scripts for the migrations).
- New documentation goes into the matching file there; no other top-level
  doc files and no per-distribution install guides.

## Security is part of every change (mandatory)

1. **Every change:** before you call a change done, commit it or open a PR,
   run the `security-check` skill on the diff and fix what it finds. Say in
   your answer which checklist points the change touched and the result
   (one or two lines are enough when nothing was found).
2. **Every release, without exception (standing rule from Dennis):**
   releases are made by semantic-release in CI when `feat`, `fix` or
   breaking-change commits reach `main` (version bump, `CHANGELOG.md`, tag
   `vX.Y.Z`, GitHub release). Before pushing such commits to `main`, run
   the `release-security-gate` skill over the whole repo, without asking
   first. Never tag by hand or edit version files / `CHANGELOG.md`; report
   the gate result and ask Dennis for the go before the push.
3. **Sensitive data, every task (standing rule from Dennis):** before you
   call a task done, commit or publish anything, run the
   `security-privacy-audit` skill (credentials, personal data, IPs and
   hostnames, Steam IDs and other account identifiers, private files) over
   the working tree, the diff, docs and the commit message, and end the
   answer with its audit summary. A `BLOCKED` finding stops the commit;
   report only category and location, never the value.
4. A finding you cannot fix in scope goes into the answer with file:line,
   impact and a proposed fix. Never silence a check, skip a test or weaken
   a validation to get green.

## Before every commit (mandatory, standing rule from Dennis)

Run the `pre-commit-checklist` skill before every `git commit`, together
with `security-check` and `security-privacy-audit`, also for small fixes:

1. Check `README.md` and the files in `docs/` against the change and
   update them in the same commit.
2. Write the commit message as a Conventional Commit (`feat:`, `fix:`,
   `docs:`, ... see the `pre-commit-checklist` skill). `CHANGELOG.md` and
   the version files are generated by semantic-release; never edit them.
3. Check dependencies and toolchain for updates and *suggest* available
   updates (do not update on your own).
4. Check the licenses of third-party code and keep the license list
   complete and current.
5. Run the `security-privacy-audit` skill on the staged changes and the
   commit message; do not commit while a check is `BLOCKED`.

Report the result of each step in one line in your answer and end with
the audit summary of `security-privacy-audit`.

## Invariants that must not break

- Every SQL statement uses placeholders (`?`, rebound for Postgres in
  `internal/database/rebind.go`). Table/column names in `fmt.Sprintf` SQL
  only from constants or a fixed allowlist, never from log or RCON data.
- Log packets are accepted only from addresses in `hlstats_Servers` and,
  with `features.log_secret` true (default), only with the server's
  `hlstats_Servers.log_secret` when one is stored
  (`internal/collector/logsecret.go`; servers without a secret and GoldSrc
  servers are not checked). The secret is set by hand (`gamewe server set
  -logsecret`, web admin, `sv_logsecret` in server.cfg); the collector never
  sets or reads `sv_logsecret` over RCON. The secret travels in plain text
  and only stops spoofed senders: treat every field of a log line (player
  names, chat, weapons, map, team, SteamIDs) as attacker-controlled input.
  Never log a log secret; `log_secret` is hidden from `gamewe_web` like
  `rcon_password`.
- The HTTP input for Counter-Strike 2 (`listen.http`, off by default;
  `internal/collector/httplog.go`) accepts a post only from a Source 2
  server of `hlstats_Servers` (sender IP plus the game port of the URL,
  `X-Forwarded-For` only from `trusted_proxies`), checked before the body
  is read; optional path token compared in constant time and never logged
  (`RedactURL`); body, line length, connections (total and per IP) and
  timeouts are bounded. Source 2 servers send no log secret.
- Text going back to a game server over RCON passes `Sanitize`
  (`internal/collector/commands.go`) or `quoted` (`rawmessage.go`):
  no `"`, `;`, control characters, bounded length.
- Bounded memory under floods: maps keyed by source/player are capped
  (see `ServeConn` in `udp.go`), queues are bounded and drop instead of
  blocking (`RconReplier`).
- Never log passwords, RCON passwords, the DB DSN or full config.
- DB users: the collector user writes, `gamewe_web` gets SELECT only and
  no `hlstats_Users`, `hlstats_Events_Rcon`, `hlstats_Events_Chat`,
  `hlstats_Servers.rcon_password`, `log_secret`, `log_secret_changed`,
  `hlstats_Events_Connects.ipAddress`
  (`internal/schema/mysql/grants.sql` and the generated Postgres file). A
  new table needs a grant decision there (a test checks this).
- The schema is compiled in (`internal/schema`, go:embed); the collector
  never reads SQL files from disk. Only `database.Migrate`
  (`internal/database/migrate.go`, `migrations.go`) changes the structure:
  `gamewe db migrate`, or `gamewe run` at start before anything else when
  `database.auto_migrate` is true (the default; never an HLstatsX database
  without versions); with it false `run` refuses to start on an old schema.
  Besides that only the explicit maintenance commands `gamewe db drop` /
  `reset` / `purge` (`internal/database/maintenance.go`) remove tables or
  rows, only of the compiled schema's tables, with confirmation. The daily
  `features.inactive_players` job (off by default, `internal/stats/inactive.go`)
  only moves whole rows between `hlstats_Players` and
  `hlstats_PlayersInactive` (`SELECT *`, the column order must stay equal;
  an integration test checks it) and deletes nothing else. Migrations
  only add (tables, columns, indexes, missing seed rows), are idempotent,
  never delete rows or drop tables/columns; released migrations are never
  changed. How to add one: `docs/DEVELOPMENT.md`, "Adding a migration".
- Secrets stay out of git: `config.yaml`, `*.pem`, `*.key`, real
  `docker-compose.yml` values are ignored; examples use `change-me`.
